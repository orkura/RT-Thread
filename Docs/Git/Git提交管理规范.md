# Git 提交管理规范

## 1. 适用范围

本规范适用于本仓库的 Git 提交信息和提交组织方式，用于保证提交历史清晰、易读、可追溯。

每个提交应只完成一个逻辑目标。无关变更应拆分为不同提交，不得为了减少提交数量而混合提交。

## 2. 提交信息格式

提交信息由标题、可选正文和可选尾注组成：

```text
<type>: <summary>

[body]

[footer]
```

当 Scope 能显著提高辨识度时，可以使用：

```text
<type>(<scope>): <summary>
```

示例：

```text
docs: 添加 Git 分支与 Agent 管理规则
fix(bsp): 修复 SPI DMA 传输超时
ci: 修复 Windows 构建环境配置
```

## 3. Type 定义

提交标题必须使用以下英文 Type 作为前缀：

| Type | 用途 |
| --- | --- |
| `feat` | 新增功能、能力或规则 |
| `fix` | 修复缺陷、错误配置或错误说明 |
| `docs` | 新增或修改文档、注释及开发规范 |
| `refactor` | 不改变外部行为的代码或结构调整 |
| `test` | 新增或修改测试及测试数据 |
| `build` | 修改构建系统、依赖或工具链配置 |
| `ci` | 修改持续集成工作流或自动化检查 |
| `perf` | 提升性能且不改变预期功能 |
| `chore` | 不属于其他类型的日常维护工作 |
| `revert` | 撤销一个或多个已有提交 |

应选择最能体现提交主要目的的 Type，不根据变更文件的扩展名机械选择。

例如，新增一份项目级开发规范属于新的仓库规则，可以使用 `docs`；修正文档中的错误命令也使用 `docs`，并在摘要中明确“修正”。

## 4. Scope 使用规则

Scope 是可选字段，用于指出变更的主要责任域。仅当 Scope 能让标题更清楚时使用，避免添加无意义或过细的 Scope。

推荐优先使用与分支管理规范一致的责任域或稳定子域：

```text
repo
agents
tools
bsp
rt-thread
docs
ci
```

示例：

```text
docs(git): 添加提交信息规范
fix(bsp): 修复 SPI DMA 传输超时
ci(windows): 修复 UCRT64 环境配置
docs(agents): 补充分支创建规则
```

一次提交涉及多个区域时，应选择主要责任域；无法确定主要责任域时，可以省略 Scope。

## 5. Summary 编写规则

摘要以中文为主，技术名词、路径、命令、API 名称和代码标识符可以保留英文。

摘要必须满足以下要求：

- 简短说明提交完成了什么，建议不超过 50 个中文字符。
- 使用明确的动词开头，例如“添加”“修复”“调整”“重构”“移除”。
- 不使用“更新内容”“修改问题”“一些调整”等无法表达实际目标的描述。
- 标题末尾不加句号。
- Type、可选 Scope 与冒号使用英文半角字符。
- 冒号后保留一个半角空格。
- 同一个提交的摘要和正文应保持语言一致，以中文为主。

推荐：

```text
docs: 添加 Git 提交管理规范
fix(tools): 修复 Keil 构建路径解析错误
refactor(rt-thread): 简化设备注册流程
```

不推荐：

```text
update
docs：更新文档。
fix: 修复问题
chore: 一些调整
```

## 6. Body 编写规则

正文不是每次提交都必须提供。简单且可以由标题完整说明的提交，可以只写标题。

存在以下情况之一时，应添加正文：

- 修改内容包含多个紧密相关的要点。
- 变更原因无法通过标题表达。
- 变更会影响构建、兼容性、配置、使用方式或后续维护。
- 修复过程包含重要限制、取舍或边界条件。
- 需要向审查者说明验证方式或未覆盖的内容。

标题与正文之间必须保留一个空行。正文应说明必要的“改了什么、为什么修改、有什么影响”，避免逐行复述代码差异。

正文可以使用简短段落或项目符号：

```text
docs: 添加 Git 分支与 Agent 管理规则

- 新增分支命名格式及生命周期规则
- 明确 AGENTS.md 和 .agents/ 的分支归属
- 增加 Agent 执行 Git 操作前的确认要求
```

需要说明原因和影响时，可以使用段落：

```text
fix(bsp): 修复 SPI DMA 传输超时

DMA 完成中断可能早于状态更新到达，导致等待逻辑误判为超时。
调整状态更新顺序，避免正常传输进入超时恢复流程。
```

## 7. Footer 使用规则

尾注用于记录需要工具解析或需要单独强调的信息，例如关联任务、破坏性变更或共同作者。

标题、正文和尾注之间分别保留一个空行。

示例：

```text
feat(rt-thread): 调整设备初始化接口

统一初始化参数并移除旧接口，以减少不同设备类型之间的差异。

BREAKING CHANGE: 旧版 rt_device_init 参数形式不再支持
```

如果项目尚未统一任务编号格式，不得自行虚构任务编号。

## 8. 提交拆分原则

提交应保持原子性，一个提交只表达一个逻辑目标。

以下内容通常应拆分提交：

- 功能实现与无关格式化。
- 缺陷修复与无关重构。
- 多个彼此独立的模块变更。
- 自动生成文件与生成器逻辑，除非两者必须同步提交。

以下内容通常可以放在同一提交：

- 功能实现及其必要测试。
- 代码变更及其同步更新的使用文档。
- 规范文件及让 Agent 遵守该规范所需的 `AGENTS.md` 引用。

不得提交临时日志、构建产物、缓存文件、密钥或与当前目标无关的本地配置。

## 9. 暂存与检查

提交前应使用明确路径暂存文件，避免默认执行 `git add .`、`git add -A` 等可能包含无关修改的命令。

推荐流程：

```powershell
git status --short
git add -- <明确的文件路径>
git diff --cached --stat
git diff --cached
git commit -m "<type>: <summary>"
```

包含正文时，可以使用多个 `-m` 参数：

```powershell
git commit `
  -m "docs: 添加 Git 提交管理规范" `
  -m "明确提交类型、中文摘要、可选正文及提交拆分规则。"
```

提交前必须确认：

1. 暂存区只包含当前逻辑目标所需的文件。
2. 提交信息符合 Type、Scope、摘要和正文规则。
3. 未覆盖或混入其他人的工作区修改。
4. 已完成与变更风险相匹配的检查或测试。

## 10. Agent 执行规则

Agent 准备创建提交时，必须：

1. 完整阅读并遵守本规范。
2. 检查工作区和暂存区，识别当前提交应包含的文件。
3. 向用户列出拟暂存文件及其项目相对路径。
4. 向用户展示完整的拟提交信息，包括必要的正文和尾注。
5. 说明暂存及提交操作的影响，并等待用户明确确认。
6. 仅暂存用户确认的文件，不默认暂存全部工作区变更。
7. 提交完成后报告提交哈希和实际提交标题。

未经用户明确授权，不得执行暂存、提交、修改提交、变基、合并、推送或其他 Git 写操作。

不得擅自使用 `git commit --amend` 修改已有提交。确需修改时，必须说明将被替换的提交及影响，并单独获得用户确认。

## 11. 示例速查

### 简单文档提交

```text
docs: 添加 Git 提交管理规范
```

### 带 Scope 的缺陷修复

```text
fix(bsp): 修复 SPI DMA 传输超时
```

### 包含关键正文

```text
ci(windows): 修复 UCRT64 工具链环境配置

- 将 C:\msys64\ucrt64\bin 放在当前进程 PATH 最前面
- 避免加载 MSYS2 Bash 或永久修改系统环境变量
```

### 包含破坏性变更

```text
feat(rt-thread): 调整设备初始化接口

统一设备初始化参数，移除已废弃的调用形式。

BREAKING CHANGE: 旧版初始化参数形式不再支持
```

## 12. 提交前检查清单

创建提交前依次确认：

1. 提交是否只包含一个逻辑目标？
2. Type 是否准确表达主要目的？
3. Scope 是否必要且足够清晰？
4. 中文摘要是否简短、具体并以动词开头？
5. 复杂变更是否添加了必要正文？
6. 正文是否说明了原因、影响或关键实现，而非简单重复差异？
7. 暂存区是否只包含已确认的文件？
8. 是否避免提交缓存、构建产物、凭据和无关修改？

符合这些条件的提交，应能让审查者在不查看完整差异的情况下理解提交的主要目的和影响。
